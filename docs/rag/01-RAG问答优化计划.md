# knowledge-retrieval RAG 问答优化计划

> 本文档基于当前 `knowledge-retrieval` 模块实现情况，梳理 RAG 问答链路的优势与不足，并给出可落地的优化建议与优先级排序。

---

## 1. 背景

`knowledge-retrieval` 当前已实现基于 LangGraph Agent 的知识问答链路：

```text
前端 SSE → query_rewrite → topic_gate → hybrid_retrieve → qa_prompt → LLM 生成
```

主要能力包括：

- 查询改写（口语规范化、指代消解、多轮拼句、错别字纠正）
- 主题闸门（路由 knowledge / cs 路径）
- 混合检索（Milvus dense ANN + BM25 + RRF + 可选精排 + 父片回填）
- 双路径生成（知识库路径 / 客服路径）
- 联网搜索补充（Tavily）

但在评测、监控、反馈闭环、兜底策略等关键环节仍存在明显缺失。

---

## 2. 当前优势

| 维度 | 说明 |
|------|------|
| 链路清晰 | 中间件职责分离，便于独立调优和扩展 |
| 改写完善 | 覆盖口语规范化、指代消解、多轮拼句、错别字纠正 |
| 检索完整 | hybrid_search + 精排 + 父片回填 + 数据权限过滤 |
| 路径分流 | knowledge/cs 两套提示词，避免无关问题污染知识库 |
| 异常不伪造 | 检索失败返回空命中，不要求模型编造 |

---

## 3. 存在的缺失与优化建议

### 3.1 Ragas 评测体系未落地

**现状**

- 已有 [知识库发布评测方案](./03-知识库发布评测方案.md) 方案文档
- 但代码层面未见自动/手动评测入口、测试集生成服务、发布门控逻辑

**优化建议**

1. 在 `knowledge-content` 中新增评测任务，读取 canary 向量运行 Ragas 指标：
   - `context_recall`
   - `context_precision`
   - `context_relevancy`
   - `faithfulness`
   - `answer_relevancy`
   - `answer_correctness`
2. 实现测试集自动生成服务，输入文档片段，输出 `(question, answer, contexts, ground_truth)`
3. 在 `EmbeddingPublishService` 中增加评测通过检查，未通过时阻止自动 promote
4. 支持手动触发评测，用于策略调优验证

---

### 3.2 生产监控未落地

**现状**

- 方案文档已规划 Langfuse Trace/Span/Generation/Score 埋点
- 代码中尚未接入 Langfuse SDK

**优化建议**

1. 接入 Langfuse CallbackHandler，自动上报：
   - Trace：一轮用户对话
   - Span：query_rewrite / topic_gate / hybrid_retrieve / qa_prompt
   - Generation：LLM 调用输入输出、Token、延迟
2. 建立核心指标看板：
   - 端到端延迟 P99
   - 分阶段延迟
   - Token 消耗
   - 检索命中率
   - 用户点踩率
   - 异常率
3. 若暂时无法部署 Langfuse，可先用本地日志 + 指标表替代

---

### 3.3 用户反馈闭环缺失

**现状**

- 无点赞/点踩接口
- 无 bad case 回流机制

**优化建议**

1. 新增用户反馈接口，记录每轮问答的 👍 / 👎
2. 将反馈写入 Langfuse Score 或本地反馈表
3. 定期抽样点踩 case，用 Ragas 离线评分
4. 把典型 bad case 加入测试集，形成闭环

---

### 3.4 拒绝/兜底策略较初级

**现状**

- 无检索命中时提示"可说明未找到或调用联网搜索"
- 未强制区分"知识库无答案"与"检索失败"
- 缺少高风险问题的特殊处理

**优化建议**

1. 明确拒绝规则：
   - 检索为空 + 未联网 → 明确告知未找到相关资料
   - 检索结果相关性低于阈值 → 拒绝回答
2. 增加 safety gate，对法律、医疗、金融等敏感问题特殊处理
3. 增加联网来源可信度判断，避免不可靠网页内容误导回答

---

### 3.5 多意图/多问题拆分缺失

**现状**

- 当前链路假设每轮只有一个问题
- 用户一句话包含多个问题时，只能用改写后的单一 query 检索

**优化建议**

1. 在 `query_rewrite` 后增加 `question_splitter` 中间件
2. 识别多意图并拆分为多个子问题
3. 每个子问题分别检索、生成，最后合并为完整回答

示例：

> 用户："帮我查下 A 文档的上传时间，再看看 B 功能怎么用。"

拆分后：

- "A 文档的上传时间是什么？"
- "B 功能怎么用？"

---

### 3.6 Citation 引用执行不严格

**现状**

- 提示词要求模型给出 `docId/chunkId` 引用
- 但无后处理校验 citation 是否真实存在于检索命中

**优化建议**

1. 解析模型回答中的 citation
2. 与 `retrieve_hits` 中的 `docId/chunkId` 比对
3. 不存在的引用：过滤、标红或触发告警
4. 在前端展示引用来源，提升可解释性

---

### 3.7 长对话压缩/上下文管理不足

**现状**

- `query_rewrite_service.py` 仅取最近 8 轮历史
- 无历史对话摘要压缩
- 超长会话未设计截断策略

**优化建议**

1. 超过一定轮数后，对历史对话做摘要压缩
2. 设计 prompt 长度上限，超限时优先丢弃较远的历史
3. 评估多轮对话下检索相关度衰减情况

---

### 3.8 缺少检索与改写缓存

**现状**

- 每次问答都重新执行：查询改写、查询向量化、混合检索、精排
- 相同 query 重复计算，成本高、延迟大

**优化建议**

1. 增加查询改写结果缓存（按原始问题 + session_id）
2. 增加检索结果缓存（按改写后 query + 用户数据权限 key）
3. 增加精排结果缓存
4. 设置合理 TTL，避免缓存污染

---

### 3.9 Prompt 版本化管理缺失

**现状**

- `prompts.yaml` 为静态配置
- 无版本号记录，难以 A/B 和回滚

**优化建议**

1. 为每个 prompt 增加 `version` 字段
2. 评测时记录 `prompt_version`
3. 支持新旧版本 A/B 对比
4. 可接入 Langfuse Prompt 管理

---

### 3.10 测试覆盖不足

**现状**

- 现有测试：query_rewrite、topic_gate、rerank、document_vector_retrieve
- 缺少 Agent 端到端、多轮对话、无命中拒绝、引用校验等测试

**优化建议**

1. 补充 Agent 端到端链路测试
2. 补充多轮对话/指代消解测试
3. 补充无命中/拒绝场景测试
4. 补充 citation 校验测试

---

## 4. 实施优先级

| 优先级 | 优化项 | 原因 |
|--------|--------|------|
| P0 | 明确拒绝/兜底策略 | 降低幻觉风险，避免业务事故 |
| P0 | 用户反馈接口 | 构建闭环基础，获取真实质量数据 |
| P1 | 生产监控（Langfuse/日志） | 没有监控无法有效优化 |
| P1 | Ragas 手动评测 | 发布前量化质量，避免策略退化 |
| P2 | 多问题拆分 | 提升复杂查询回答质量 |
| P2 | 检索/改写缓存 | 降成本、降延迟 |
| P2 | Citation 校验 | 提升可信度，避免伪造引用 |
| P3 | 对话压缩 | 支持长会话场景 |
| P3 | Prompt 版本化管理 | 便于 A/B 和回滚 |

---

## 5. 总结

`knowledge-retrieval` 的 RAG 问答链路**骨架完整、设计合理**，在查询改写、混合检索、路径分流等方面已具备较高完成度。

下一步应重点补齐：

1. **评测**：Ragas 评测 + 测试集生成 + 发布门控
2. **监控**：Langfuse 生产监控 + 核心指标看板
3. **反馈**：点赞/点踩 + bad case 回流
4. **兜底**：明确拒绝策略 + safety gate

补上这四块后，整体链路才能从"能跑"演进为"可运营、可优化"。
