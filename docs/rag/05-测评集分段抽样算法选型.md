# 测评集出题：分段抽样算法选型

> 用途：为 knowledge-admin「测评集生成 Agent」选定**目录种子抽样**算法。  
> 范围：只讨论「从最多约 10 万分段里如何挑出给 LLM 看的种子集」；正文读取预算、难度配额、Ragas 指标不在本文展开。  
> 关联：`docs/rag/03-知识库发布评测方案.md`（出题 Agent + 分段 MCP）；实现落点 `knowledge_admin/agents/utils/segment_directory.py`。

---

## 1. 问题定义

### 1.1 输入 / 输出

| | 说明 |
|--|------|
| **输入** | 单个 `doc_id`；底层分段按 `file_id + chunk_order` 有序，总量可达 \(N \approx 10^5\) |
| **约束** | 禁止全量 list 进模型上下文；MCP `list` 仍是分页 API；正文另有 `get`/`search` 预算 |
| **输出** | 固定规模种子目录 \(K\) 条（建议 **20～50**）：`chunk_id`、`chunk_order`、短预览、`total`、抽样说明 `note` |
| **后续** | Agent 对种子 `get` 读正文；不够时再 `search`/`get` **扩展**；最后 `save_dataset_items` |

### 1.2 要优化什么

1. **覆盖**：种子尽量摊开在整篇文档（含首尾），避免只看到开头。  
2. **成本**：RPC/DB 次数、返回给 LLM 的 token 可控、可复现。  
3. **可扩展**：simple 题可只用种子；hard 跨段题允许 Agent 主动扩展。  
4. **工程匹配**：尽量复用现有 `list_document_segments` 分页，少改 content DAO。

### 1.3 非目标（本期不做）

- 用评测分数自动反传调整抽样（active learning）  
- 全库跨文档抽样（测评集绑定单 `doc_id`）  
- 把聚类质心直接当 ground_truth 来源（仍须 LLM 出题）

---

## 2. 总流程（与算法无关的外壳）

三种算法换的只是「怎么挑种子」这一步，前后外壳一样：

1. 创建测评集，绑定一个 `doc_id`，打开分段 MCP。
2. 用抽样算法挑出 K 条目录预览，并带上文档总段数。这次 `list` 直接把**已经抽好的种子**放进 Agent 上下文，模型不用自己翻页。
3. Agent 从种子里挑段，用 `get_document_segments` 读正文（计入预算）。
4. 材料够就合成题目（simple / medium / hard）。不够、或者要跨段，再用 `search` 或补一次 `get` 扩展，然后回到上一步看够不够。
5. 出完题调用 `save_dataset_items` 落库。
6. 如果正文预算先用完，就走降级：在已有种子里再抽一个子集，用 LLM 或启发式凑题，同样落库。

**设计要点**

- **种子抽样 = 确定性/半确定性算法**，不交给 LLM 决定「抽哪 50 个下标」。  
- **是否扩展 = LLM 决策**（工具：`get` / `search`），受正文预算硬限制。  
- `list` 一次调用应对 Agent 暴露「已抽好的种子」，而不是让模型自己翻页。

## 3. 候选算法（细化）

### 3.1 算法 A：均匀下标抽样（Even / Stride Index）

#### 做法（白话）

一篇文档可能有上万段，模型一次看不完，所以只**均匀挑几十条**给它看，别全挤在开头。

1. **先问「一共有多少段？」**  
   调一次 `list`，只要 1 条就够——目的是拿返回里的总数 `N`，不是那 1 条本身。例如 `N = 10000`。

2. **决定要挑几条**  
   配置里有个上限（默认 **50**，可改成 20）。文档段数不够就少抽：  
   - 文档有 10000 段 → 抽 50  
   - 文档只有 12 段 → 最多抽 12  
   记实际条数为 \(K = \min(\text{配置上限}, N)\)。

3. **从开头到结尾等间隔点名**  
   不是随机抽，而是像在尺子上均匀插 `K` 根钉子：第一根钉开头，最后一根钉结尾，中间等距。  
   例：共 101 段、抽 5 条 → 下标大约是 `0, 25, 50, 75, 100`。  
   再对每个下标定点 `list` 取那一条目录。

一句话：**摸清总数 → 决定抽几条（不超过配置上限）→ 首尾必含、中间等距点名。**

#### 复杂度与代价

| 项 | 量级 |
|----|------|
| MCP/DB 次数 | \(O(K)\)（外加 1 次 probe；idx=0 可复用 probe） |
| 返回 token | \(O(K \times preview)\)，与 \(N\) 无关 |
| 可复现 | 同 \(N,K\) 下标完全确定 |

#### 优点 / 缺点

- ✅ 实现简单、易测、与当前 MCP 零协议变更  
- ✅ 10 万段也只打约 K 次定点读，不扫表  
- ❌ 不感知「语义重复」：模板段、页眉页脚仍可能进种子  
- ❌ 多 `file_id` 时，若某文件极长，可能「看起来均匀」但短文件被摊薄（仍按全局下标）

#### 适用

单文档、结构相对线性；要先跑通评测闭环。**当前实现即本算法。**

---

### 3.2 算法 B：分层均匀抽样（Stratified by file_id / 章节桶）

#### 做法（白话）

这是抽样里的**分层比例抽样**（proportional allocation）。层就是子文档。它不是「每个子文档一样多」，而是：**样本里的段数结构尽量接近全文**。全文里占 40% 段数的子文档，50 条里大约占 20 条。段数多的多分，这是这个算法的定义。

1. **先拿到每个子文档有多少段**  
   总数、各层段数一次统计拿完。不要在 admin 里一页页翻。

2. **按段数比例分 K 条**  
   某一层的条数 = `K × 该层段数 ÷ 总段数`。先发整数，剩下的零头按小数从大到小各加 1，直到正好 K 条。这就是最大余数法。层数比 K 多时，理论条数不到 1 的层多数是 0，不会强行每层 1 条。

3. **每一层内部用系统抽样（算法 A）**  
   这一层分到几条，就在它自己的段里从头到尾等间隔点名。分到 0 的层跳过。

4. **按全文顺序交给 Agent**  
   后面读正文、不够再搜索，和算法 A 一样。

**例子：300 个子文档，抽 50 条，总段数 10 万。**

| 子文档 | 段数 | 理论条数 | 实际 |
|--------|------|----------|------|
| 手册 A | 4 万（40%） | 20 | 20 |
| 手册 B | 2 万（20%） | 10 | 10 |
| 手册 C | 1 万（10%） | 5 | 5 |
| 其余 297 个，每个约 100 段 | 合计 3 万（30%） | 每个约 0.05 | 小数最大的 15 个各 1 条，其余 0 |

手册 A 先拿到 20 条，是因为它占了全文四成，不是算错。300 层只有 50 个名额，绝大多数短子文档是 0。

一句话：**先按段数比例把名额分到各子文档，再在每个分到名额的子文档内部等间隔抽。**

#### 复杂度与代价

| 项 | 量级 |
|----|------|
| 额外依赖 | 需要 **分层统计 API**（一次聚合查询，理想 \(O(\#files)\)） |
| 定点读取 | 仍约 \(O(K)\) |
| 可复现 | 同直方图 + \(K\) 可复现 |

#### 优点 / 缺点

- ✅ 样本的段数结构接近全文：长子文档多分、短子文档少分，这是比例分配本身  
- ✅ 仍是确定性算法，无向量依赖  
- ❌ 要动 content（统计或按 file 分页）；分层键选错（只有一个 file）时退化为 A  
- ❌ 实现与测试量明显高于 A  

#### 适用

同一 `doc_id` 下经常挂多个 `file_id`（多 PDF/多爬取页合并）且线上已出现「题全出在某一个大文件」。

### 3.3 算法 C：向量聚类抽质心（Embedding Diversity Sampling）

#### 做法（白话）

均匀抽不看内容像不像。同一套模板、页眉页脚、重复说明，可能被抽进好几条。聚类是：**先看每段在说什么（用已经算好的向量），把意思相近的归成一堆，每堆只留最能代表这堆的那一条。**

1. **前提：这篇文档的向量已经算好**  
   建议用 canary 那次向量化任务，和评测发布用的是同一套。向量还没好，就退回算法 A。

2. **段太多时，先缩小再聚类**  
   十万段全部做聚类太重。可以先按算法 A 的办法均匀抽出几千条（比如 2 千到 5 千），只对这批做聚类。

3. **聚成大约 K 堆，每堆留 1 条**  
   意思相近的段进同一堆。每堆挑离「这堆中心」最近的那一段当作种子，再补上短预览交给 Agent。

4. **后面出题不变**  
   Agent 仍然用 `get` 读正文，不够再用 `search`。这次搜索和聚类用的是同一套向量，扩展时更不容易又搜回同一类话。

一句话：**向量没好就用 A；好了就先缩小样本、按意思分堆、每堆留一条代表。**

#### 复杂度与代价

| 项 | 量级 |
|----|------|
| 依赖 | Milvus + embedding 任务完成；与评测 canary 对齐 |
| 计算 | 预抽样 \(N'\) 上 k-means，显著重于 A/B |
| 延迟 | 秒～十秒级（视 \(N'\)），不适合「同步点创建就出题」除非异步化 |
| 可复现 | 需固定随机种子与 \(N'\)；浮点/实现差异可能导致轻微抖动 |

#### 优点 / 缺点

- ✅ 语义覆盖最好，重复模板段不易扎堆  
- ✅ 与「检索质量」同一套向量空间，评测种子更接近真实召回多样性  
- ❌ 强依赖向量化完成；出题链路与发布/canary 耦合  
- ❌ 运维与故障面大（Milvus 抖动、维度变更、task 切换）  
- ❌ hard 跨段仍可能需要 search；聚类不自动保证「可因果拼接」的邻段  

#### 适用

单文档极大、重复多、已稳定跑 canary，且产品明确要「覆盖率/多样性」指标时再上。

## 4. 对比与选型

### 4.1 对照表

| 维度 | A 均匀下标 | B 分层均匀 | C 向量聚类 |
|------|------------|------------|------------|
| 实现成本 | 低（已落地） | 中（要统计 API） | 高 |
| 对 \(N=10^5\) | 仅 \(O(K)\) 定点读 | \(O(K)\) + 一次直方图 | 预抽 + 聚类 |
| 多 file 均衡 | 弱 | **强** | 中（语义向，不保证按 file） |
| 语义去重 | 弱 | 弱 | **强** |
| 依赖 | 仅 MCP list | list + 分层统计 | Milvus + embedding |
| 可复现 | 强 | 强 | 中 |
| 与现网匹配 | **最佳** | 文档形态复杂时值得上 | 二期/三期 |

### 4.2 怎么选

三种算法最后都接到同一套 Agent 扩展（`get` / `search` + 正文预算）。先问这两句：

1. **出题必须等 canary 向量算完吗？**  
   必须等、而且接受和向量化绑在一起 → 用算法 C。  
   测评集要能单独跑、不依赖向量 → 看下一问。

2. **同一篇文档是不是经常由多个文件、多本手册拼起来？**  
   还不明显，或者基本是单文件 → 用算法 A，均匀抽，`K = 50`。  
   已经出现「题几乎全出在某一个大文件里」→ 用算法 B，按 `file_id` 分层。

### 4.3 建议结论（供评审拍板）

| 阶段 | 算法 | 配置建议 |
|------|------|----------|
| **本期（推荐拍板）** | **A 均匀下标** | `DIRECTORY_SAMPLE_COUNT = 50`（可降为 20 做对照实验） |
| **观察到多 file 偏科后** | 演进 **B** | 分层键优先 `file_id`；无多 file 时自动 fallback A |
| **覆盖率成为明确 KPI 后** | 可选 **C** | 仅异步出题任务启用；失败 fallback A |

**不建议本期直接上 C**：测评集生成规格已写明可独立于切分/向量化流程；C 会破坏该边界。

## 5. 与现有实现的对齐

| 模块 | 现状 | 选型后 |
|------|------|--------|
| `segment_directory.sample_directory` | 算法 A（`even_indices` + 定点 list） | 维持 A；常量 `DIRECTORY_SAMPLE_COUNT` |
| `list_document_segments` 工具 | 一次调用返回种子 | 保持；文案强调「种子非全量」 |
| `prompts.yaml` | 种子 + LLM 扩展 | 保持；不把「抽哪些下标」交给模型 |
| 降级 `_degrade` | 对种子再 `sample_evenly` | 与 A 一致；上 B/C 后降级应复用同一抽样入口 |
| content MCP | 仅分页 list | A 无需改；B 需加直方图；C 需 retrieval/Milvus 读入口 |

## 6. 实验与验收（选型落地后）

对同一 `doc_id`（建议：单文件小文档、多文件大文档各 1 份）固定随机种子外的参数：

1. **分布**：种子 `chunk_order` 分位数（P0/P25/P50/P75/P100）是否拉开。  
2. **偏科**：按 `file_id` 看种子占比是否接近该文件的真实段数占比。A、B 都应贴近段数占比；B 是按层定额后再层内等间隔，不靠全局下标碰巧落到某个文件。  
3. **出题**：自动生成后难度比、hard 题 `used_chunk_ids≥2` 比例、人工抽检「是否同一模板段换皮」。  
4. **成本**：单次生成 MCP 调用次数、耗时、list 返回字符数。

**通过线（建议）**

- A：\(N>1000\) 时 list 相关调用 ≤ \(K+1\)，返回行数 ≤ \(K\)。  
- 切换 B 的触发：人工抽检连续 3 次「>70% 题出自同一 file_id」，且该 file 占文档段数 &lt;40%。
