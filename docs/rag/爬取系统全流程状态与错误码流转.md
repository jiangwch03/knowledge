# 1.output_node 任务创建流程

用户确认策略后，`output_node` 调用 `WebCrawlerTaskService.create_task()`：粗估页数 → 检查重复爬取 → 落库任务及关联 → 发送 `crawl.task.pending` 消息触发后台执行。其中**保存爬取任务配置参数**（`crawl_config` JSON）是整个流程最核心的处理——后续执行阶段的全部爬取策略均依赖此配置。

```mermaid
sequenceDiagram
    participant User as 用户
    participant Agent as output_node<br/>(LangGraph)
    participant TaskSvc as WebCrawlerTaskService
    participant DB as 数据库
    participant MQ as MessageStream

    User->>Agent: 确认爬取策略
    Agent->>TaskSvc: create_task()
    TaskSvc->>TaskSvc: 从爬取配置中提取max_pages作为预估页数(Agent已分析过)
    TaskSvc->>DB: 检查当前会话是否已成功爬取过该URL(重复则抛异常)
    Note over TaskSvc,DB: 核心步骤：保存爬取任务配置参数
    TaskSvc->>DB: 保存爬取任务表(crawl_config JSON, 预估页数, status=PENDING)
    TaskSvc->>DB: 保存会话-任务关联表
    TaskSvc->>DB: 保存消息-任务关联表
    TaskSvc->>MQ: produce("crawl.task.pending")
    TaskSvc-->>Agent: task_id
    Agent-->>User: SSE done 事件(task_id)
```

## 消息

- **topic**：`crawl.task.pending`
- **载荷**：`{task_id}`
- **后续**：由 handle_crawl_task_pending 消费，进入执行阶段

# 2.handle_crawl_task_pending 任务执行流程

消费 `crawl.task.pending` 消息后，获取分布式锁防止并发执行，进入 `execute_task` 后先查询任务状态进行**幂等守卫**——仅 `PENDING` 状态才继续执行，其余状态直接跳过（防止消息重复投递导致已处理完成的任务被重执行）。校验通过后调用 `WebCrawlerTaskExecutorService.execute_task()` 编排完整执行链路：标记开始 → 流式爬取+逐页上传 → 标记终态。

```mermaid
sequenceDiagram
    participant Consumer as handle_crawl_task_pending
    participant Pipeline as CrawlPipelineService
    participant Redis as Redis
    participant DB as 数据库
    participant MQ as MessageStream

    Consumer->>Redis: 获取分布式锁(防止同一任务并发执行)
    Consumer->>DB: 步骤0: 幂等守卫—查询任务状态
    alt 状态不是PENDING
        Consumer->>Redis: 释放分布式锁
        Consumer->>Consumer: 直接退出(消息重复投递,已非待执行状态)
    else 状态是PENDING
        Consumer->>DB: 更新任务状态(status=RUNNING)
        
        loop 流式爬取(逐页)
            Consumer->>Pipeline: 爬取一页+后处理(重试场景传入skip_urls)
            Pipeline->>Redis: 检查取消标志(每页爬取结果返回后)
            alt 检测到取消标志
                Pipeline-->>Consumer: 停止爬取, 正常结束
                Note over Consumer,Redis: 状态已由定时任务标记为FAILED(TIMEOUT), 无需重复更新, 消费者正常结束
            else 未取消, 继续处理
                Pipeline-->>Consumer: 爬取结果(成功/失败+错误码)
                Consumer->>DB: 保存URL记录表(逐条, 首次新增/重试更新, 含错误码)
                Consumer->>DB: 更新任务进度(success_count/failed_count)
            end
        end

        alt 全部成功
            Consumer->>DB: 更新任务状态(status=COMPLETED, progress=100)
            Consumer->>MQ: produce("crawl.document.pending", 触发文档合并)
        else 有失败
            Consumer->>DB: 更新任务状态(status=FAILED, error_code=ALL/PARTIAL_CRAWL_FAILED)
            Note over DB: 后续由失败重试定时任务承接, 执行规则重试或升级为USER_DECISION
        end
    end
```

> **重试场景说明**：重试时会先加载上次已成功URL集合（skip_urls），传入 Pipeline 跳过这些URL的爬取和后处理，避免重复工作。首次执行时 skip_urls 为空集，其他逻辑完全一致。

## CrawlPipelineService 子流程

`CrawlPipelineService` 编排两大阶段：**网页爬取**（Crawl4aiClient 流式获取页面）→ **后处理**（CrawlPostProcessorService 图片转储+Markdown上传），每爬完一页立即进入后处理并释放内存。

```mermaid
sequenceDiagram
    participant Pipeline as CrawlPipelineService
    participant Crawl4ai as Crawl4aiClient
    participant Redis as Redis
    participant PostProc as CrawlPostProcessorService
    participant MinIO as MinIO

    Pipeline->>Crawl4ai: 流式请求爬取
    Note over Crawl4ai: 解析爬取配置，生成爬取策略

    loop 每收到一页结果
        Crawl4ai-->>Pipeline: yield 单页爬取结果
        Pipeline->>Redis: 检查取消标志(发现则停止爬取)

        alt 阶段一：网页爬取失败或无内容
            Pipeline-->>Pipeline: 透传失败信息(含error_code)，跳过后处理
        else 阶段一：网页爬取成功(markdown+图片)
            Note over Pipeline,PostProc: 进入阶段二：后处理
            Pipeline->>PostProc: process_single(爬取结果)

            loop 每张图片
                PostProc->>PostProc: 下载图片二进制
                PostProc->>MinIO: 上传图片
                PostProc->>PostProc: 替换markdown中图片URL为MinIO链接
            end

            PostProc->>MinIO: 上传处理后的markdown文件
            PostProc-->>Pipeline: 返回object_name(MinIO路径)
        end
    end
```

### 两大阶段职责

| 阶段 | 执行者 | 说明 |
|------|--------|------|
| 网页爬取 | Crawl4aiClient | 流式获取页面内容，每爬完一页 yield 一次（含 markdown、图片引用、状态码等） |
| 后处理 | CrawlPostProcessorService | **仅在爬取成功时执行**：提取图片 → 下载并上传 MinIO → 替换 markdown 链接 → 上传 markdown |

### 后处理详细步骤

| 步骤 | 说明 |
|------|------|
| 提取图片引用 | 从 markdown 中匹配 `![alt](url)` 语法 |
| 下载图片 | HTTP 下载原始图片二进制（超时 30s） |
| 上传图片到 MinIO | 路径：`crawler/{task_id}/images/{hash}.{ext}` |
| 生成图片描述 | 调用 LLM 为无 alt 文本的图片生成描述（可选） |
| 替换 markdown | 将图片 URL 替换为 MinIO 链接 |
| 上传 markdown | 路径：`crawler/{task_id}/pages/{url_hash}.md` |

## 任务表状态变更

| 时机 | 状态 | error_code |
|------|------|-----------|
| 开始执行 | RUNNING | - |
| 全部成功 | COMPLETED | null |
| 全部失败 | FAILED | ALL_CRAWL_FAILED |
| 部分失败 | FAILED | PARTIAL_CRAWL_FAILED |
| 被取消（超时兜底触发） | FAILED | TIMEOUT（由定时任务设置） |

## 消息

- **topic**：`crawl.document.pending`（仅全部成功时发送）
- **载荷**：`{task_id, target_url}`
- **后续**：由 handle_crawl_document_pending 消费，进入文档合并阶段

# 3.超时取消机制（定时任务）

由 **`WebCrawlerTaskScheduler.timeout_fallback`** 超时兜底定时任务（每5分钟）触发，扫描 RUNNING 超过阈值的任务：
1. 将任务状态标记为 `FAILED`，error_code=`TIMEOUT`
2. 在 Redis 中设置取消标志（key: `crawl:task:cancel:{task_id}`，TTL: 10分钟）
3. `CrawlPipelineService` 每收到一页爬取结果后检查此标志，发现后停止爬取，消费者正常结束

# 4.handle_crawl_document_pending 文档合并流程

消费 `crawl.document.pending` 消息后，获取分布式锁防止重复处理，前置校验任务状态和文档记录后，从 URL 记录中重建爬取结果，调用 `CrawlerDocumentService.persist_documents()` 完成文档落库。其中**保存文档表**（`knowledge_document`）是整个合并流程最核心的处理——将散落在 MinIO 的各页 markdown 收拢为一条可检索的知识库文档。

```mermaid
sequenceDiagram
    participant Consumer as handle_crawl_document_pending
    participant DocSvc as CrawlerDocumentService
    participant Redis as Redis
    participant DB as 数据库
    participant MinIO as MinIO

    Consumer->>Redis: 获取分布式锁(防止同一任务文档重复处理)
    Consumer->>DB: 步骤1：查询任务状态
    alt 状态不是CONVERT_FAILED且不是COMPLETED
        Consumer->>Redis: 释放分布式锁
        Consumer->>Consumer: 直接退出（不满足处理条件）
    else 状态是CONVERT_FAILED或COMPLETED
        Consumer->>DB: 步骤2：查询文档表
        alt 文档记录已存在
            Consumer->>Redis: 释放分布式锁
            Consumer->>Consumer: 直接退出（已落库）
        else 无文档记录
            Consumer->>DB: 查询爬取成功的网页url记录数据(status=SUCCESS)
            Consumer->>Consumer: 合并文档(从doc_key/title/url)
            Consumer->>DocSvc: persist_documents(爬取结果)

            alt 合并成功
                alt 单页爬取结果
                    Note over DocSvc: 直接使用后处理阶段已上传的MinIO文件，无需重新上传
                    Note over DocSvc,DB: 核心步骤：保存文档表
                    DocSvc->>DB: 保存文档表(knowledge_document, status=CONVERTED)
                    DocSvc->>DB: 更新同标题旧版本(is_latest=0)
                else 多页爬取结果
                    loop 逐页
                        DocSvc->>MinIO: 下载该页markdown
                        DocSvc->>DocSvc: 追加写入临时文件(页间用---分隔)
                    end
                    DocSvc->>MinIO: 上传合并后的markdown文件
                    Note over DocSvc,DB: 核心步骤：保存文档表
                    DocSvc->>DB: 保存文档表(knowledge_document, status=CONVERTED)
                    DocSvc->>DB: 更新同标题旧版本(is_latest=0)
                end
                Consumer->>DB: 更新任务状态(status=CONVERTED)
            else 合并失败
                Consumer->>DB: 更新任务状态(status=CONVERT_FAILED, error_code=DOC_PERSIST_ERROR)
                Note over Consumer,DB: 后续由消息重试或兜底定时任务承接
            end
        end
    end
```

# 5.retry_failed_tasks 重试定时任务

定时扫描 `FAILED` 与 `CONVERT_FAILED` 状态的任务，通过分层策略自动重试或升级为用户人工决策。

```mermaid
sequenceDiagram
    participant Scheduler as retry_failed_tasks
    participant Redis as Redis
    participant DB as 数据库
    participant MsgStream as MessageStream

    Scheduler->>Redis: 获取分布式锁(LockKey.crawl_task_retry_job_key, expire=300s, 防止批次并发)

    Note over Scheduler,MsgStream: ─── 阶段一：CONVERT_FAILED 文档合并重试 ───
    Scheduler->>DB: 查询所有CONVERT_FAILED状态的任务
    loop 遍历每个文档合并失败任务
        Scheduler->>MsgStream: 直接发送crawl.document.pending(触发合并重试)
        Note over Scheduler,MsgStream: 不修改状态、不递增retry_count
    end

    Note over Scheduler,MsgStream: ─── 阶段二：FAILED 爬取失败重试 ───
    Scheduler->>DB: 查询所有FAILED状态的任务
    loop 遍历每个爬取失败任务
        Scheduler->>DB: 查询任务详情(task_id, error_code, retry_count)
        Scheduler->>Scheduler: 分层决策(见下方决策流程图)
        alt 决策结果=规则重试
            Scheduler->>DB: 重置状态PENDING(retry_count++)
            Scheduler->>MsgStream: 发送crawl.task.pending(触发重新执行)
        else 决策结果=人工决策
            Scheduler->>DB: 标记USER_DECISION(终态)
        end
    end
```

### retry_failed_tasks(try_auto_retry) 决策流程图

```mermaid
flowchart TD
    START["开始重试决策<br/>try_auto_retry(task_id)"] --> Q1{"是否已达规则重试上限？<br/>retry_count >= rule_retry_limit?"}

    Q1 -- "已达上限" --> OUT1["标记 status=USER_DECISION<br/>（保留原 error_code）"]
    Q1 -- "未达上限" --> Q2{"是否因超时被取消？<br/>error_code = TIMEOUT"}

    Q2 -- "是：超时取消<br/>无需查URL记录" --> DO_RETRY["规则重试<br/>· status = PENDING<br/>· retry_count++<br/>· 发送 crawl.task.pending"]
    Q2 -- "否" --> Q3{"是否为爬取失败类错误？<br/>error_code ∈ {ALL_CRAWL_FAILED,<br/>PARTIAL_CRAWL_FAILED}"}

    Q3 -- "否：非爬取失败类错误<br/>如 BIZ_ERROR / EXEC_ERROR<br/>CONSUMER_ERROR / DOC_PERSIST_ERROR" --> OUT2["标记 status=USER_DECISION<br/>（保留原 error_code）"]
    Q3 -- "是：爬取失败" --> Q4{"URL记录是否存在<br/>瞬时故障类错误码？<br/>(BROWSER_CRASH / PAGE_TIMEOUT /<br/>CONNECTION_RESET / RATE_LIMITED /<br/>CLOUDFLARE_CHALLENGE)"}

    Q4 -- "有：可自动恢复" --> DO_RETRY
    Q4 -- "无：重试无意义" --> OUT3["标记 status=USER_DECISION<br/>（保留原 error_code）"]
```

> **分布式锁策略**：Job 级互斥锁（`LockKey.crawl_task_retry_job_key`），expire=300s、timeout=0、renew=True。新的定时触发若未抢到锁则直接跳过，等下一轮再来，防止上一批次尚未执行完毕时重复触发。

> **CONVERT_FAILED 处理**：仅重新发送 `crawl.document.pending` 消息，由 handle_crawl_document_pending 消费者重新执行文档合并流程。**不修改任务状态、不递增 retry_count**。

> **DIRECT_RETRY_TASK_ERROR_CODES**（直接重试，不查URL记录）：`TIMEOUT` — 仅限超时取消场景：定时任务超时兜底将 RUNNING 任务标记为 FAILED+TIMEOUT，重试时无需查询 URL 记录表，直接重置执行。

> **RULE_RETRY_ERROR_CODES**（URL记录级瞬时故障）：`BROWSER_CRASH` / `PAGE_TIMEOUT` / `CONNECTION_RESET` / `RATE_LIMITED` / `CLOUDFLARE_CHALLENGE`

> **规则重试**（`_rule_retry`）：重置 `status=PENDING`、递增 `retry_count`、清空错误信息，再发布 `crawl.task.pending` 消息触发重新执行。

> **标记 status=USER_DECISION**（终态）：原 error_code 保持不变（如 `ALL_CRAWL_FAILED`、`TIMEOUT`），用户在任务详情页跳转聊天框，通过 Agent 调整策略后手动重试或放弃。以下任一条件触发此分支：
> 1. `retry_count` 已达规则重试上限（`crawl4ai_rule_retry_limit`）
> 2. 任务级 error_code 非 `ALL_CRAWL_FAILED` / `PARTIAL_CRAWL_FAILED`（非爬取类错误，自动重试无意义）
> 3. URL 记录中无瞬时故障类错误码（失败原因不可自动恢复）

# 6.handle_task_decision 用户决策流程

`retry_failed_tasks` 将任务标记为 `status=USER_DECISION` 后，用户通过前端进入任务详情页，调用 `POST /crawler/task/{task_id}/decision` 接口做出决策：**重试**（复用原配置重新执行）或 **放弃**（软删除）。

```mermaid
sequenceDiagram
    participant User as 用户
    participant API as WebCrawlerTaskController<br/>(/decision)
    participant Redis as Redis
    participant Service as WebCrawlerTaskService
    participant DB as 数据库
    participant MsgStream as MessageStream

    User->>API: POST /crawler/task/{task_id}/decision<br/>{action: "retry" | "abandon"}
    API->>Redis: 获取分布式锁(LockKey.crawl_task_key(task_id),<br/>expire=30s, timeout=10s)

    alt 未获取到锁
        API-->>User: 响应"任务正在处理中，请稍后重试"
    else 获取锁成功

        API->>Service: 查询任务状态
        alt status != USER_DECISION
            API-->>User: 响应"当前任务状态不允许决策操作"
        else status = USER_DECISION

            alt action="retry"（重试）
                API->>Service: retry_task(task_id)
                Service->>DB: 步骤1：校验任务存在
                Service->>DB: 步骤2：重置 status=PENDING, retry_count++, 清空错误信息
                Note over Service,DB: 与自动规则重试走同一路径<br/>不受 retry_count 上限限制
                Service->>MsgStream: 步骤3：发送 crawl.task.pending(触发重新执行)
                Service-->>API: 成功
                API-->>User: 响应"已重新加入执行队列"

            else action="abandon"（放弃）
                API->>Service: delete_task(task_id)
                Service->>DB: 步骤1：校验任务存在
                Service->>DB: 步骤2：软删除(del_flag, update_by=当前用户)
                Service-->>API: 成功
                API-->>User: 响应"已放弃该任务"
            end

            API->>Redis: 释放分布式锁
        end
    end
```

> **触发入口**：用户在任务列表页看到 `status=USER_DECISION`（"待用户决策"），点击进入详情查看原始失败原因（`error_code` + `error_message`），在聊天框内通过 Agent 确认决策后提交。

> **重试与自动重试的异同**：
> - 相同点：都调用 `WebCrawlerTaskService.retry_task()`，重置 `status=PENDING`、递增 `retry_count`、发送 `crawl.task.pending`
> - 不同点：用户手动重试**不受 `retry_count` 上限限制**，可无限次触发
>
> **crawl_config 调整**：`TaskDecisionVo` 预留了 `crawl_config` 字段，当前实现中重试仍复用原配置，尚未接入调整参数后重试的逻辑。

> **放弃即软删除**：调用 `WebCrawlerTaskDao.soft_delete()` 设置 `del_flag` 标记，非物理删除，数据可追溯。

> **分布式锁**：复用 `LockKey.crawl_task_key(task_id)`，与消费者侧同一把锁——决策处理期间消费者不会同时消费同一任务；expire=30s、timeout=10s，锁释放后消费者才能拾取 PENDING 任务执行。
