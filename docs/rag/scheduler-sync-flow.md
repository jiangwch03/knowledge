# 定时任务注册与同步调度机制

## 一、项目启动：定时任务注册流程

系统启动时，所有 Worker 实例会竞争同一把**分布式锁**（Application Lock），只有抢到锁的实例成为 Leader，负责启动调度器并加载任务。

```
所有 Worker 启动
    ↓
竞争 Application 锁（Redis）
    ├── 抢到锁的 Worker → 成为 Leader
    │       ↓
    │   启动 APScheduler
    │       ↓
    │   从数据库加载本应用（app_scope）下所有 status='0' 的任务
    │       ↓
    │   逐个注册到调度器（按 cron 表达式周期性执行）
    │       ↓
    │   启动两个后台机制：
    │       ① 每 10 秒自动从数据库同步一次任务状态
    │       ② BroadcastService 启动 @subscriber 监听，等待其他实例的同步通知
    │
    └── 未抢到锁的 Worker → 成为普通 Worker
            ↓
        不启动调度器，不加载任务
        但保留 Redis 连接，用于后续发布广播通知(只有admin项目有用,任务编辑功能在admin)
```

**关键设计**：数据库是任务状态的**唯一真相源**，Leader 启动时只是将数据库中已启用的任务镜像到内存调度器。如果 Leader 挂了，其他 Worker 抢到锁后会重新加载，数据不会丢失。

## 二、运行时：Admin 项目操作任务并发布广播

**核心原则**：Admin 后台的所有任务操作（新增、修改、删除、执行一次）都遵循**"只写数据库，再发广播通知 Leader 处理"**的统一模式。Service 层绝不直接操作调度器，调度器的增删改完全由 Leader 负责。

### 2.1 新增任务

```
用户提交新增任务
    ↓
校验（Cron 表达式、白名单、唯一性等）
    ↓
写入数据库
    ↓
提交事务
    ↓
发布全局广播通知（action=sync, 携带 app_scope）
    ↓
任意项目的 Leader 收到 → 从数据库同步任务状态 → 注册到调度器
```

### 2.2 修改任务

```
用户提交修改任务
    ↓
校验
    ↓
更新数据库
    ↓
提交事务
    ↓
发布全局广播通知（action=sync）
    ↓
任意项目的 Leader 收到 → 从数据库同步 → 移除旧任务 → 注册新配置
```

### 2.3 删除任务

```
用户提交删除任务
    ↓
从数据库删除
    ↓
提交事务
    ↓
发布全局广播通知（action=sync）
    ↓
任意项目的 Leader 收到 → 从数据库同步 → 从调度器移除
```

### 2.4 执行一次

```
用户点击"执行一次"
    ↓
查询数据库确认任务存在
    ↓
发布全局广播通知（action=execute_once, 携带 job_id）
    ↓
任意项目的 Leader 收到 → 查询数据库任务详情 → 通过 APScheduler 立即执行一次
```

**为什么"执行一次"也要走广播？**

如果直接在接收到请求的实例上执行，会有两个问题：
1. **执行位置不确定**：请求打到 Worker 上，任务就在 Worker 进程里跑，可能缺少目标模块（尤其是多项目独立部署时）
2. **与 Cron 执行位置不一致**：Cron 任务一定在 Leader 上跑，"执行一次"也应该在 Leader 上跑，保证执行环境一致
3. **执行任务所述app_scope不确定**: 任务定义不一定在admin项目中

## 三、Leader 监听广播并执行同步

各项目 Leader 通过 `BroadcastService` 框架的 `@subscriber` 装饰器注册广播 handler，由框架统一的后台 listen loop 驱动消息接收。当任意实例发布广播时，Leader 的 handler 会收到消息并触发同步。

### 3.1 广播消息的传输链路

```
[Admin 后端实例]
    ↓
调用 SchedulerUtil.broadcast_scheduler_sync(app_scope) 或 broadcast_execute_job_once(job_id, app_scope)
    ↓
内部改调 BroadcastService.publish() 向 Redis 全局通道发布消息：
    {"app_scope": "knowledge-admin", "action": "sync", "worker_id": "xxx"}
    或
    {"app_scope": "knowledge-admin", "action": "execute_once", "job_id": 123, "worker_id": "xxx"} (执行一次)
    ↓
[Redis Pub/Sub 广播到所有订阅者]
    ↓
BroadcastService listen loop 收到消息 → 分发给 @subscriber handler
    ↓
handler 检查 app_scope 是否匹配本应用？
    ├── 不匹配 → 忽略（应用隔离）
    └── 匹配 → 根据 action 分发处理：
            ├── action="sync" → 触发内部同步流水线
            └── action="execute_once" → 查询数据库 → 立即执行一次任务
```

### 3.2 Leader 内部同步流水线

Leader 收到广播后，不会立即刷数据库，而是经过两层保护机制：

```
收到同步请求
    ↓
标记同步待执行（_sync_pending = True）
    ↓
防抖等待 0.5 秒
    └── 如果这 0.5 秒内又有新请求，合并为一次
    ↓
检查距离上次同步是否超过 2 秒？
    ├── 不足 2 秒 → 等待到满 2 秒再执行
    └── 已满 2 秒 → 立即执行
    ↓
从数据库读取当前任务状态
    ↓
与 APScheduler 内存中的任务做三向对比：
    ① 数据库已禁用，但调度器还有 → 移除
    ② 数据库有，但调度器没有 → 添加
    ③ 两边都有，但配置不同 → 更新（移除后重加）
```

**两层保护的意义**：

- **防抖（0.5 秒）**：防止用户连续点击或批量操作导致频繁刷库，合并为一次同步
- **节流（2 秒）**：无论多频繁地收到通知，Leader 刷数据库的最小间隔是 2 秒，保护数据库压力

## 四、三个流程的关联关系

这三个流程不是孤立的，而是围绕**"数据库为真相源、Leader 负责调度、广播通知驱动同步"**的核心设计协同工作：

```
┌─────────────────────────────────────────────────────────────────┐
│                        系统启动阶段                               │
│  Worker 竞争锁 → Leader 加载数据库任务 → 调度器开始运行            │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│                        运行时阶段                                 │
│  ┌─────────────┐    写数据库      ┌─────────────────────┐        │
│  │ Admin项目用户│ ─────────────→  │ 数据库（唯一真相源）    │        │
│  │ 操作任务     │                 └──────────┬──────────┘        │
│  └─────────────┘                           │                    │
│       ↓                                    │                    │
│  发布全局广播通知 ←───────────────────────────┘                    │
│       ↓                                                         │
│  各项目Leader 监听广播 ──┬─ action=sync → 防抖/节流 → 同步调度器     │
│                    └─ action=execute_once → 立即执行一次任务       │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│                        Leader 切换阶段                            │
│  旧 Leader 丢失锁 → 停止调度器 → 新 Leader 抢到锁 → 重新加载数据库     │
│  （无论切换时机如何，新 Leader 加载的都是最新数据）                    │
└─────────────────────────────────────────────────────────────────┘
```

## 五、多 Worker 机制下的关键保障

### 5.1 为什么只有 Leader 能消费广播？

**设计层面**：BroadcastService 的 listen loop 只在 Leader 启动时创建，普通 Worker 根本不启动监听。

**防御层面**：即使出现极端情况（如锁丢失后状态未即时切换），`@subscriber` handler 内部也有 `_is_leader` 检查，非 Leader 会直接忽略消息。

### 5.2 应用隔离如何保障？

Admin 和 Rag 共享同一个 Redis，它们会订阅同一个全局广播通道。广播消息中携带了 `app_scope` 字段：

```
Admin 发布同步广播：  {"app_scope": "knowledge-admin", "action": "sync"}
Admin 发布执行广播：  {"app_scope": "knowledge-admin", "action": "execute_once", "job_id": 123}

Leader 收到消息后检查：
    if msg_app_scope != 本应用:
        跳过
    else:
        根据 action 字段分发处理
```

这样 Admin 的任务变更不会触发 Rag 的同步，反之亦然。

### 5.3 Leader 挂了怎么办？

分布式锁有过期时间。如果 Leader 进程崩溃或网络断开：

1. 锁到期自动释放
2. 其他 Worker 在重试循环中抢到锁
3. 新 Leader 启动，重新从数据库加载任务
4. 由于数据库是唯一真相源，调度器状态与数据库始终保持一致

### 5.4 为什么不需要 Worker 直接通知 Leader？

早期设计中可能存在 Worker 通过独立通道通知 Leader 的机制，但当前实现已全部收敛到**全局广播通道**：

- **简化**：所有同步走统一通道，维护成本低
- **解耦**：Worker 不需要知道当前谁是 Leader，只负责发广播
- **可靠**：Redis Pub/Sub 保证消息至少送达一次（即使 Leader 短暂断开重连也能收到）
