# Embedding 任务性能优化记录

> 日期：2026-07-22  
> 背景：task#4（约 10 万分段）跑起来后，管理端列表等查询明显变慢；排查后确认与 Milvus 索引无关。

---

## 一、现象

- Embedding 任务（尤其大文档）运行期间，管理端「Embedding 任务」列表等接口响应变慢、页面长时间 loading。
- 当时 task#4 进度约 `17k~22k / 103640`，仍处于**阶段一：向量写 MySQL**，尚未大批量刷 Milvus。

---

## 二、结论摘要

| 方向 | 结论 |
|------|------|
| Milvus 索引 | **不是原因**。`AUTOINDEX` + 标量 `INVERTED` 正常 Finished/Loaded；当时 collection 约 345 行，task#4 尚未 upsert |
| MySQL 索引 | **主因之一**。`knowledge_document_segment` 线上仅剩 `PRIMARY` + `idx_embedding_id`，热路径全表扫描 |
| 事件循环 | **主因之二**。`embeddings.embed_documents()` 同步阻塞 HTTP，在 async 流水线里直调，堵住 FastAPI 事件循环 |

---

## 三、问题 1：MySQL 分段表索引丢失

### 3.1 现场

```text
SHOW INDEX FROM knowledge_document_segment
→ 仅 PRIMARY(id)、idx_embedding_id(embedding_id)

EXPLAIN ... WHERE task_id=? AND skip_embedding=0 AND status='STORED' AND del_flag='0'
ORDER BY file_id, chunk_order LIMIT 100
→ type=ALL，约 9.5 万行，Using where; Using filesort
```

热路径（每批拉待 Embedding / COUNT）均走全表扫描。表结构按 ORM 形态重建过时，未带上 DDL 中的 `idx_task_id` 等索引。

### 3.2 处理

1. 线上补齐索引（已执行）。
2. 写入最终建表语句：`sql/upgrade_document_embedding.sql`、`sql/upgrade_knowledge_content.sql`。
3. ORM `KnowledgeDocumentSegment.__table_args__` 声明同名 Index，避免再丢。

新增/恢复索引：

| 索引 | 列 | 用途 |
|------|-----|------|
| `idx_task_id` | `task_id` | 按任务过滤 |
| `idx_doc_id` | `doc_id` | 按文档过滤 |
| `idx_doc_release` | `doc_id, release_tag` | 发布标签查询 |
| `idx_chunk_id` | `chunk_id` | 业务分片关联 |
| `idx_task_embed_queue` | `task_id, skip_embedding, status, del_flag, file_id, chunk_order` | Embedding 拉批 / COUNT，覆盖 ORDER BY |

### 3.3 效果（本机实测）

| SQL | 优化前 | 优化后 |
|-----|--------|--------|
| 拉批 `LIMIT 100`（task#4） | ~117ms，全表扫描 + filesort | ~0.9ms，`idx_task_embed_queue` + Using index |
| 同类 COUNT | ~100ms 量级 | ~27ms（走复合索引） |

## 四、问题 2：同步 Embedding 堵住事件循环

### 4.1 原因

流水线外层是 `async`（consumer → `process_pending` → `embed_and_store`），但 LangChain `Embeddings.embed_documents` 是**同步**方法，内部阻塞 HTTP。

原先：

```python
vectors = embeddings.embed_documents(texts)  # 无 await，占满事件循环约数秒/批
```

同进程内其它 HTTP（任务列表等）会一起卡住。Milvus 写入侧本来就用了 `asyncio.to_thread`，对比之下 Embedding 调用漏了。

### 4.2 处理

`vector_store_service.py`：

```python
vectors = await asyncio.to_thread(embeddings.embed_documents, texts)
```

需**重启 knowledge-content** 后生效。

## 六、后续注意

1. 大批量刷 Milvus 后若检索变慢，再单独看 growing segment / compaction（本次未改 Milvus）。
2. 失败任务有调度自动重试；手工置 `EMBED_FAILED` 后若不希望被拉起，需停相关 job 或改调度逻辑。

## 七、批并发加速（2026-07-22 续）

### 7.1 问题

阶段一 Embedding / 阶段二刷 Milvus 原先**按批串行**：一批 `embed_documents`（同步 HTTP，批内再按 `API_CHUNK_SIZE=10` 拆请求）完成才拉下一批。10 万段 × ~4s/批 → 墙钟时间过长。

### 7.2 方案

单任务内 **id 入队 + 固定工人池**（谁干完谁立刻领下一批，不等整波结束）：

1. 先查出全部待处理分片 id，按 `batch_size` 切成队列。
2. 启动 `concurrency` 个工人；每个工人从队列取一批 → Embedding/刷库 → 立刻取下一批。
3. 进度用 `asyncio.Lock` 串行回写。

实现拆分（便于 review）：

| 文件 | 职责 |
|------|------|
| `vector_store_service.py` | 编排：校验 collection → 调并发阶段 → finalize |
| `embedding_concurrent_service.py` | 队列工人池 + 阶段一 Embedding + 阶段二刷 Milvus |

配置（`.env`）：

| 变量 | 默认 | 说明 |
|------|------|------|
| `EMBEDDING_EMBED_CONCURRENCY` | `4` | 工人数（同时在飞批次数）；过大易触发模型限流 |
| `EMBEDDING_EMBED_BATCH_SIZE` | `100` | 每批条数 |

与全局 `SEMAPHORE_EMBEDDING_PIPELINE_SIZE`（多任务并发）正交：前者管**一个任务内部**批并行，后者管**同时跑几个任务**。

### 7.3 注意

- 通义等限流严格时把 concurrency 降到 `2`；限流宽松可试 `6~8`。
- 某批失败 → 任务 `EMBED_FAILED`；已成功批为 `EMBEDDED`，重试续跑剩余 `STORED`。
- 改配置后需重启 knowledge-content。
