## 一、存储策略

| 存储层 | 存储内容 | 设计原则 |
|--------|---------|---------|
| **MinIO** | Markdown 文件 + 图片二进制 | 全量内容存储，DB 不存大字段 |
| **MySQL url_record** | status / minio_url / title / error 等元数据 | 单条 ~700B，轻量化设计 |
| **MySQL knowledge_document** | 文档元数据（doc_key 指向 MinIO） | 单条 ~1KB |

## 二、单页数据大小拆解

### 2.1 Markdown 文件（MinIO）

| 页面类型 | 最小 | 典型 | 最大 |
|---------|------|------|------|
| 纯文档页（无图、纯文字） | 5 KB | 10 KB | 20 KB |
| 技术博客（含代码块） | 10 KB | 20 KB | 40 KB |
| 含表格/代码块的文档页 | 20 KB | 35 KB | 80 KB |
| Wiki 页面 | 8 KB | 15 KB | 30 KB |

**典型值：~20 KB/页**

### 2.2 图片文件（MinIO）

| 页面类型 | 图片数量 | 单张大小 | 单页图片总量 |
|---------|---------|---------|-------------|
| 纯文档页 | 0-1 张 | 50-100 KB | 0-100 KB |
| 技术博客（含截图） | 2-5 张 | 50-200 KB | 200 KB-1 MB |
| 公式/流程图密集页 | 5-15 张 | 30-150 KB | 500 KB-3 MB |
| 架构文档（大量架构图） | 3-8 张 | 100-300 KB | 500 KB-2 MB |

**典型值：3-5 张/页，~500 KB/页**

> **图片去重**：同一站点的 logo、导航图标、通用示意图会跨页重复，MinIO 使用 MD5 哈希命名天然去重，实际图片存储可比估算低 **20-30%**。

### 2.3 数据库记录

#### url_record 单条记录

| 字段 | 类型 | 典型大小 |
|------|------|---------|
| id | bigint | 8 B |
| task_id | bigint | 8 B |
| url | varchar(1000) | ~200 B |
| status | varchar(20) | ~10 B |
| minio_url | varchar(500) | ~200 B |
| title | varchar(255) | ~100 B |
| status_code | int | 4 B |
| error_code / error_message | varchar/text | ~50 B（成功时为 NULL） |
| retry_count | int | 4 B |
| 审计字段 (create_by/time/update_by/time/del_flag) | — | ~100 B |
| **合计** | | **~700 B** |

#### knowledge_document 单条记录

| 字段组 | 典型大小 |
|--------|---------|
| 主键 + 外键 | 24 B |
| doc_title / doc_name / doc_type | ~200 B |
| doc_key (MinIO 路径) | ~200 B |
| source_url | ~200 B |
| 状态 + 版本 | ~30 B |
| 审计字段 | ~100 B |
| **合计** | **~1 KB** |

## 三、按网站规模分级评估

### 3.1 综合评估表

| 网站类型 | 典型页面数 | URL 记录数 | MinIO 存储 | DB url_record | DB document |
|---------|-----------|-----------|------------|--------------|-------------|
| 个人博客 / 小型文档站 | 10-50 | ~50 条 | ~25 MB | ~35 KB | ~50 KB |
| 公司官网 / 中型博客 | 50-200 | ~200 条 | ~100 MB | ~140 KB | ~200 KB |
| 中型文档站 (Vue/React 级别) | 200-1,000 | ~1,000 条 | ~500 MB | ~700 KB | ~1 MB |
| 大型文档站 / Wiki | 1,000-5,000 | ~5,000 条 | ~2.5 GB | ~3.5 MB | ~5 MB |
| 超大型站点 | 5,000-20,000 | ~20,000 条 | ~10 GB | ~14 MB | ~20 MB |

> **计算公式**：MinIO ≈ 页面数 × 500KB（markdown 20KB + 图片 500KB，去重后约 480KB）

### 3.2 典型场景详细拆解

#### 场景 A：爬取技术文档站

```
目标: https://docs.example.com
配置: max_depth=3, max_pages=500, include_external=false

实际爬取: ~300 页
├── Markdown 文件: 300 × 20KB     =   6 MB
├── 图片文件:     ~800 张 × 80KB   =  64 MB（去重后约 50 MB）
├── MinIO 总计:                    ≈  56 MB
├── DB url_record: 300 × 700B     ≈ 210 KB
└── DB document:   300 × 1KB      ≈ 300 KB
```

#### 场景 B：爬取技术博客

```
目标: https://blog.example.com
配置: max_depth=2, max_pages=200, include_external=false

实际爬取: ~120 页
├── Markdown 文件: 120 × 15KB      =   1.8 MB
├── 图片文件:     ~500 张 × 120KB   =  60 MB（去重后约 48 MB）
├── MinIO 总计:                     ≈  50 MB
├── DB url_record: 120 × 700B      ≈  84 KB
└── DB document:   120 × 1KB       ≈ 120 KB
```

#### 场景 C：爬取大型 Wiki

```
目标: https://wiki.example.com
配置: max_depth=4, max_pages=5000, include_external=false

实际爬取: ~3,000 页
├── Markdown 文件: 3000 × 15KB      =  45 MB
├── 图片文件:     ~5000 张 × 80KB    = 400 MB（去重后约 300 MB）
├── MinIO 总计:                      ≈ 345 MB
├── DB url_record: 3000 × 700B      ≈ 2.1 MB
└── DB document:   3000 × 1KB       ≈   3 MB
```

## 四、关键影响因素

### 4.1 页面数控制（由 deep_crawl_strategy 决定）

| 参数 | 影响 | 建议值 |
|------|------|--------|
| `max_pages` | 硬上限，直接决定 URL 记录天花板 | 500（默认） |
| `max_depth` | 深度限制，depth=1 仅首页+直链页，depth=3 可达数百页 | 2-3 |
| `include_external` | 是否爬外链，开启后页面数可能暴增 10x+ | false |
| `filter_chain` | URL 模式过滤，可精确控制爬取范围 | 按业务配置 |

### 4.2 单页大小控制（由内容类型决定）

| 内容特征 | Markdown 大小 | 图片大小 |
|---------|--------------|---------|
| 纯文字文档 | 5-15 KB | 0 |
| 含代码块的文档 | 15-40 KB | 极少 |
| 含截图的博客 | 10-25 KB | 500 KB-1 MB |
| 公式/流程图密集 | 20-50 KB | 1-3 MB |
| 大型表格页面 | 30-80 KB | 极少 |

### 4.3 后处理对存储的影响

| 环节 | 存储变化 |
|------|---------|
| 图片下载 → MinIO 上传 | 新增图片存储（原始大小） |
| LLM 图片描述生成 | Markdown 中 alt 文本变长，影响可忽略 |
| 图片 URL 替换为 MinIO URL | Markdown 大小基本不变 |
| Markdown 上传 MinIO | 新增 Markdown 文件存储 |

## 五、存储容量规划

### 5.1 单任务上限

按 `max_pages=5000` 的极端场景：

| 存储层 | 容量 | 是否构成瓶颈 |
|--------|------|-------------|
| MinIO | ~2.5 GB | 取决于磁盘配额，通常无压力 |
| MySQL url_record | ~3.5 MB | 无压力 |
| MySQL knowledge_document | ~5 MB | 无压力 |

### 5.2 多任务累积

| 累计任务数 | MinIO 总量 | DB 总量 | 建议 |
|-----------|-----------|--------|------|
| 10 个中型任务 | ~1 GB | ~3 MB | 无需关注 |
| 50 个中型任务 | ~5 GB | ~15 MB | 正常范围 |
| 200 个中型任务 | ~20 GB | ~60 MB | 关注 MinIO 磁盘 |
| 1000 个中型任务 | ~100 GB | ~300 MB | MinIO 需扩容或清理策略 |

### 5.3 结论

| 维度 | 结论 |
|------|------|
| **DB 分库分表** | **不需要**。单条 url_record ~700B，即使 10 万条记录也仅 ~70MB，远未触及 MySQL 单表瓶颈 |
| **MinIO 容量** | 主要瓶颈。按每个任务 50-500MB 估算，需关注磁盘配额 |
| **清理策略** | 建议对已删除任务（del_flag=2）关联的 MinIO 对象定期清理 |
| **图片去重** | MinIO MD5 命名天然去重，无需额外处理 |
