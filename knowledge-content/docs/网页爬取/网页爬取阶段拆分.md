# 网页爬取阶段拆分

> 记录日期：2026-08-01  
> 目的：把当前「探站 + 定范围 + 配参 + 试爬 + 正式爬 + 清洗 + 落库 + 运维」捆在一起的链路，拆成可独立打磨效果的阶段；先单阶段做好，再考虑整合编排。  
> 相关：[当前卡点：网站特征分析 & 文档清洗](./网站特征分析与文档清洗卡点.md)、[Firecrawl 单页/整站参考](./Firecrawl单页抓取与整站爬取.md)、[网页爬虫流程](../../../docs/rag功能流程说明/网页爬虫流程.md)

## 1. 为什么要拆

当前架构里，Planning 一侧同时承担：

- 探站观察（robots / sitemap / fetch / 渲染探针 / 反爬）
- 站点类型判断与用户追问（版本 / 语言 / 板块 / 登录）
- 生成完整 `strategy_config`
- 试爬与调参闭环
- 失败修复

正式执行侧则是 MQ 管道：批量爬取 → 图片后处理 → 落库；**缺少独立、稳定的正文清洗层**。

结果是：

1. **阶段只存在于 prompt 纪律，没有产物契约**——配参可以推翻探站事实，试爬凑合过也能进正式任务  
2. **无法单独优化效果**——无法说「本周只把探站准确率拉起来」  
3. **一处漂，全链路脏**——特征偏 → 策略歪 → 噪声 Markdown 入库  

拆分原则：**每个阶段只对一个产物负责；对话侧可做成 Agent，执行侧优先做成服务。**

## 2. 总览

```text
  对话侧（适合拆 Agent，逐个练效果）          执行侧（偏服务，不必硬做成 Agent）
  ═══════════════════════════════════════     ════════════════════════════════
       ┌─────────┐
  URL─▶│ ① 探站   │  事实：结构 / 反爬 / 候选类型
       └────┬────┘
            ▼
       ┌─────────┐
       │ ② 定范围 │  决策：爬哪块、版本、语言、登录
       └────┬────┘
            ▼
       ┌─────────┐
       │ ③ 配策略 │  产物：strategy_config
       └────┬────┘
            ▼
       ┌─────────┐
       │ ④ 试爬验收│  裁判：配置能否产出可用正文
       └────┬────┘
            ▼ HITL 确认
       ┌─────────┐     ┌─────────┐     ┌─────────┐
       │ ⑤ 正式爬 │────▶│ ⑥ 清洗  │────▶│ ⑦ 落库  │
       └─────────┘     └─────────┘     └─────────┘
            ▲
            │ 失败样本回灌
       ┌─────────┐
       │ ⑧ 任务运维│  暂停 / 重试 / 改范围 / 合并
       └─────────┘
```

| 阶段 | 唯一目标 | 输入 | 输出（契约） | 形态建议 |
|------|----------|------|--------------|----------|
| ① 探站 | 弄清站点事实 | 目标 URL（及用户补充入口） | `SiteReport` | Agent / 工具链 |
| ② 定范围 | 和人对齐「爬什么」 | `SiteReport` + 用户意图 | `ScopeContract` | 薄 Agent 或强制表单 |
| ③ 配策略 | 写出可执行配置 | `ScopeContract`（+ 报告摘要） | `strategy_config` | Agent |
| ④ 试爬验收 | 证明配置可用 | `strategy_config` + seed | `TrialVerdict` | Agent 闭环或独立裁判服务 |
| ⑤ 正式爬 | 按配置批量抓取 | 已确认任务 + 配置 | 原始页 Markdown（对象存储） | 服务（现有执行器） |
| ⑥ 清洗 | 把页变成可入库正文 | 原始 Markdown | 干净 Markdown + 质量分 | **优先规则服务**（可后加 LLM） |
| ⑦ 落库 | 进入知识库 | 通过质量门槛的页 | `knowledge_document` + 文件子表 | 服务（现有） |
| ⑧ 运维 | 管任务生命周期 | 任务状态 / 失败样本 | 暂停、重试、改范围、合并 | Supervisor（现有） |

## 3. 阶段说明

### 3.1 ① 探站（Site Understanding）

**目标**：只产出可复核的站点事实，不做最终爬取范围承诺，不写完整 Crawl4AI JSON。

**建议能力**（可复用现有工具，但出口收束为报告）：

- robots / sitemap
- HTTP 样本页 +（按需）渲染探针
- 反爬等级、代理是否必要
- 结构事实：链接规模、正文量、控制组件、交互线索
- 候选站点类型与 `crawl_implications`（建议标签，非最终裁定）

**产出 `SiteReport`（概念字段）**：

- `urls_sampled`：实际看过的页面（应支持多页，而不仅首页）
- `structure` / `controls` / `interactive_elements`
- `site_type_candidates`（带分）
- `anti_crawl`、`robots`、`sitemap_summary`
- `open_questions`：需要人回答的点（版本、登录、板块等）

**明确不做**：

- 不输出最终 `strategy_config`
- 不替用户决定 include/exclude
- 不直接提交正式爬取

**「做好」的验收方向**：

- 多栏目采样后，文档区 / 营销区判断不易被首页带偏
- 探针强信号默认进入报告，模型改写须标注理由
- 报告可供下一阶段只读消费，无需再跑完整探站

---

### 3.2 ② 定范围（Scope Alignment）

**目标**：把「爬什么」变成显式契约，和「怎么爬」解耦。

**产出 `ScopeContract`（概念字段）**：

- `seed_url`（正式入口，须落在目标板块）
- `include_patterns` / `exclude_patterns`
- `version` / `language`（若适用）
- `auth`：是否需要登录及凭证占位（不含把登录页误当目标站）
- `max_pages` / `depth` 等业务上限（产品语义，不一定等于底层全部参数）
- `user_confirmed_at`：人确认标记

**明确不做**：

- 不写 `wait_for` / `css_selector` / hooks 细节（留给 ③）
- 不替代试爬验收

**「做好」的验收方向**：

- 营销首页 + 只 include `/docs` 这类矛盾在进 ③ 之前被拦住或被追问改入口
- 版本 / 语言 / 板块一旦确认，后续阶段不得静默放宽

**形态**：可先做成「探站出口 checklist + HITL 表单」，不一定单独 Agent；稳定后再抽。

---

### 3.3 ③ 配策略（Strategy Authoring）

**目标**：在范围契约约束下，生成合法、可试爬的 Crawl4AI 配置。

**输入约束**：

- 必须以 `ScopeContract` 为硬边界（seed / include / exclude / 版本锁）
- 可只读 `SiteReport` 摘要；**禁止重新发明与报告冲突的站点真相**（若冲突，回退 ①/②，不硬编）

**产出**：

- `strategy_config`：`browser_config` + `crawler_run_config` + 可选 `hooks`
- `strategy_summary`：给人看的策略说明（非执行必需）

**明确不做**：

- 不扩大已确认范围
- 不跳过试爬直接宣称可上线（上线门禁在 ④ + HITL）

**「做好」的验收方向**：

- 配置通过结构校验（现有 validate 能力可下沉为本阶段门）
- 同类站点可复现合理默认（文档站 / 博客 / SPA 等），而不是每次随机一套

---

### 3.4 ④ 试爬验收（Trial Gate）

**目标**：当裁判，不负责「再讲一遍站点故事」。

**产出 `TrialVerdict`（概念字段）**：

- `passed` / 失败码列表
- `sample_url`、正文长度、标题/标题层级是否存在
- `seed_in_scope` / `expansion_ok`（范围相关）
- `content_quality`：是否像登录页、空壳、菜单页（应强于「有字」）
- `config_fingerprint`：供正式提交门禁绑定

**与 ③ 的关系**：

- 推荐形态：**策略 Agent 内配参 ↔ 试爬闭环（有限轮次）**，但验收标准与指纹门禁应可独立实现、独立单测
- 硬失败不得签发「可提交」；软问题（如缺标题）策略需产品化，避免「脏样本也能 verified」

**明确不做**：

- 不创建正式长任务
- 不落知识库

---

### 3.5 ⑤ 正式爬（Batch Execute）

**目标**：按已确认配置稳定批量抓取；吞吐与可靠性优先。

**现状**：MQ 待执行 → 执行器流式逐页 → URL 记录 + 进度；相对成熟。

**阶段边界**：

- 输入：HITL 确认后的任务 + 通过 ④ 指纹门禁的配置
- 输出：每页原始 Markdown（及抓取元数据），**不在本阶段做知识向清洗**
- 暂停 / 超时 / 失败状态机保持现有任务表语义

**「做好」的验收方向**：

- 幂等、可暂停、可续跑、失败可归因
- 不把「正文是否适合 RAG」混进抓取成功标准（交给 ⑥）

---

### 3.6 ⑥ 清洗（Content Cleaning）

**目标**：打开页面与洗正文分离——Crawl4AI 负责抓到可用 Markdown；本阶段负责稳定去噪与质量门槛。

**建议最小能力**：

1. 去明显导航 / 页脚 / Cookie / 重复页眉页脚  
2. 保留正文与标题层级  
3. 质量判断：过短、无标题、几乎全是菜单词 → 失败或降级，不直接当优质文档  
4. 与现有图片后处理衔接（图链路可保持在清洗之后或之中的固定步骤）

**产出**：

- `cleaned_markdown` + `quality_score` / `quality_flags`
- 未过门槛的页：标记失败码，不进入「优质入库」路径

**明确不做**：

- 不回头修改整站 `strategy_config`（系统性问题回灌 ③/④ 或 ⑧）
- 不替代向量化 / 切分

**「做好」的验收方向**：

- 即使 ①/③ 偶尔配歪，入库噪声明显下降  
- 有可回归的样例集（脏页 → 期望干净页 / 期望拒收）

> 优先级说明：与卡点文档一致，**清洗层可先于完美特征分析落地**。

---

### 3.7 ⑦ 落库（Ingest）

**目标**：将通过质量门槛的页写入知识库文档模型。

**现状**：爬取完成后投递文档落库消息；1 主表 + N 文件子表等既有设计可保留。

**阶段边界**：只消费「可入库」页；不对抓取策略负责。

---

### 3.8 ⑧ 任务运维（Task Ops）

**目标**：任务级生命周期与人机协作，不承担探站/配参细节。

**能力**（与现 Supervisor 对齐）：

- 查询 / 暂停 / 恢复 / 删除
- 失败重试、改范围、合并已爬结果
- 将失败样本回灌到 ③/④（修复配置），而不是在运维 Agent 内重写整份探站逻辑

**「做好」的验收方向**：

- 管任务与爬新站两条线不串（网址查任务仅用于防重复等既有约定）
- 写操作继续走 HITL

---

## 4. 建议的落地粒度（避免拆太碎）

不必八个阶段都做成 Agent。推荐先落 **4 个可独立练效果的单元**：

| 单元 | 覆盖阶段 | 说明 |
|------|----------|------|
| **A. 探站 Agent** | ① | 出口只有 `SiteReport` |
| **B. 范围澄清** | ② | 可先做薄（表单 / checklist）；稳了再 Agent 化 |
| **C. 策略 Agent** | ③ + ④ | 配参 ↔ 试爬有限闭环；契约进、Verdict 出 |
| **D. 清洗服务** | ⑥ | 优先规则 + 质量门槛，不必先上 LLM Agent |
| 正式爬 / 落库 / 运维 | ⑤ ⑦ ⑧ | 保持服务 + 现有 Supervisor |

最小三块起步：**A / C / D**；② 作为 A→C 之间的强制确认产物。

整合（统一 Supervisor 编排、一次对话跑完全程）应在各单元单独达标后再做。前期甚至允许人工把 `SiteReport` 交给策略 Agent，用来验证契约是否够用。

## 5. 阶段间契约（整合前先冻结）

```text
SiteReport ──▶ ScopeContract ──▶ strategy_config ──▶ TrialVerdict
                                                         │
                                                    HITL + 指纹
                                                         ▼
                                              Task ──▶ Raw pages
                                                         ▼
                                              Clean pages + quality
                                                         ▼
                                                   Knowledge docs
```

硬规则建议：

1. **③ 不得静默改写 ② 的范围**；要改必须回到 ② 重新确认  
2. **没有通过 ④ 的指纹，不得创建/重试正式任务**（与现试爬门禁同方向，边界更清晰）  
3. **⑥ 未过质量门槛的页，不得当成功优质文档进 ⑦**  
4. **① 的多页采样与强信号默认采纳**，避免只看首页、模型随意改类型  

---

## 6. 与「效果不好」的对应

| 体感问题 | 优先打磨阶段 |
|----------|----------------|
| 入库内容脏（导航/页脚/菜单） | ⑥ 清洗 |
| 爬错板块、首页当文档入口 | ① 探站 + ② 定范围 |
| 空壳/登录页也能提交 | ④ 试爬验收 |
| 配置玄学、同站每次不一样 | ③ 配策略（只消费契约） |
| 抓不到 / 403 / 超时 | ⑤ 执行可靠性 + ① 反爬事实 |
| 任务状态乱、重试绕门禁 | ⑧ 运维 + ④ 指纹门禁 |

---

## 7. 明确不做（本拆分阶段）

- 不优先自研第二套抓取引擎；底层继续 Crawl4AI  
- 不优先「先轻量 HTTP 再升级浏览器」作为主线（见卡点文档）  
- 不把扩展重点放在未验证前的大一统 Agent 提示词堆叠  
- 整合编排晚于单阶段效果达标  

---

## 8. 建议推进顺序

| 顺序 | 事项 | 预期 |
|------|------|------|
| 1 | 冻结本章契约字段（报告 / 范围 / 配置 / 试爬结论 / 清洗质量） | 后续拆 Agent 有接口可依 |
| 2 | 落地 ⑥ 清洗服务 + 入库质量门槛 | 知识库内容体感最快变好 |
| 3 | 收束 ① 探站出口为 `SiteReport`（含多页采样） | 特征可单独评估 |
| 4 | 抽出 ③+④ 策略闭环，强制吃 `ScopeContract` | 配置可回归、可门禁 |
| 5 | 再考虑 Supervisor 级联编排（整合） | 单阶段已证明有效后再粘合 |
