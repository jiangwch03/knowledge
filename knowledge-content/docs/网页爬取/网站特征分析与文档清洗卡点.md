# 当前卡点：网站特征分析 & 文档清洗

> 记录日期：2026-08-01  
> 前提：底层继续用 Crawl4AI；暂不考虑「先轻量 HTTP 再升级浏览器」；扩展靠 Crawl4AI 服务部署加机器。

## 1. 结论（先看这）

当前两个主卡点：

1. **网站特征分析效果不好** → 策略容易配歪  
2. **文档清洗效果不好** → 入库内容噪声大  

两者是绑在一起的：**特征看不准 → 清洗/爬取配置也容易错**。

在不做轻量抓取的前提下，建议优先级：

1. **先补正文清洗 + 质量门槛**（用户最容易感知变好）  
2. **再收紧特征分析**（多页采样、默认听探针）  
3. 站点类型细分类、复杂交互识别往后放  

---

## 2. 现状判断

### 2.1 网站特征分析

已有能力：

- 规划 Agent + 探针（robots / sitemap / HTTP / 渲染探针 / 反爬等）
- 试爬质量门
- 人工确认后再正式爬

效果不好的常见原因：

- 往往只看首页，营销页 ≠ 文档区 ≠ 产品区  
- 「要不要上浏览器」等门闩信号偏弱  
- 探针算了分，最终类型/策略仍多由大模型自由决定，容易漂  
- 试爬更多验证「有没有抓到字」，较少验证「类型/范围判对没」

### 2.2 文档清洗

已有「后处理」主要做的是：

- 从 Markdown 提图片  
- 下载图片 → 上传 MinIO  
- 可选 LLM 图片描述  
- 再把 Markdown 存 MinIO  

对应代码大致在：`CrawlPostProcessorService`（图片链路为主）。

**真正的正文清洗（去导航/页脚/Cookie/菜单噪声）并没有形成独立、稳定的一层。**  
更多依赖：

- Crawl4AI 自带 Markdown / 过滤能力  
- Agent 配出来的 `strategy_config`  

所以：策略配歪，或站点结构复杂时，清洗效果就会差。

---

## 3. 特征分析：优化方向

### 3.1 目标先降级

先别死磕「准确识别 8 种站点类型」。  
优先把这 4 个问题做准：

1. 要不要登录  
2. 只爬哪一块（如文档路径、版本路径）  
3. 要不要点展开 / 翻页  
4. 是不是空壳页（有没有真正正文）

### 3.2 具体改法（投入小、收益大）

1. **多看几页再下结论**  
   首页 + sitemap 或站内链接里 2～3 个不同栏目，再聚合判断。

2. **探针结论默认采用**  
   探针已有明显倾向时，默认用它的类型/含义标签；大模型要改必须写清理由。

3. **弱化不可靠信号**  
   少用「页面里有没有脚本」这类几乎永远为真的信号当关键门闩。

4. **试爬当裁判**  
   除了「有没有字」，增加：是否像登录页、正文是否明显长过菜单、有没有标题层级等。  
   不过关先重配，再进正式长任务。

### 3.3 可借鉴 Firecrawl 的点（仅限特征相关）

Firecrawl 并没有「预爬前跟用户聊站点类型」的能力，但可借鉴：

- 用多 URL / 站点目录信息辅助判断，而不是只看一页  
- 用「结果像不像有效内容」做校验，而不是只信事前分类名  

本项目的 Agent 沟通、试爬、人工确认继续保持，这是优势。

---

## 4. 文档清洗：优化方向

### 4.1 原则

**打开页面（Crawl4AI）和洗正文分开。**  
Crawl4AI 负责抓到可用 Markdown；本系统再做一轮稳定清洗，再入库。

### 4.2 建议补的一层（最小可用）

在现有图片后处理之前或之后，增加「正文清洗」步骤，例如：

1. 去掉明显导航 / 页脚 / Cookie 提示等噪声块  
2. 去掉过短、重复的页头页尾  
3. 保留正文与标题层级  
4. 清洗后做质量判断：太短、无标题、几乎全是菜单词 → 标失败或降级，不直接当优质文档入库  

说明：图片处理仍保留；清洗解决的是「字干不干净」，不是「图存没存」。

### 4.3 和特征分析的关系

- 特征准 → include/exclude、过滤策略更准 → Crawl4AI 初稿更干净  
- 即使特征偶尔不准，独立清洗层也能兜一层底  

两手都要，但**清洗层可以先落地**，不依赖特征分析一次做完美。

---

## 5. 明确不做（当前阶段）

- 不优先做「轻量 HTTP 抓取再升级浏览器」  
- 不把扩展重点放在自研第二套抓取引擎  
- Crawl4AI 服务部署 + 加机器，作为吞吐扩展手段  

当前精力集中在：

- 特征分析更稳  
- 正文清洗更干净  
- 调度 / 去重 / 任务可控继续保持  

---

## 6. 建议落地顺序

| 顺序 | 事项 | 预期体感 |
|------|------|----------|
| 1 | 独立正文清洗 + 入库质量门槛 | 知识库内容明显更干净 |
| 2 | 多页采样 + 探针默认采纳 | 少爬错范围、少配错策略 |
| 3 | 强化试爬验收（空壳/登录/无正文） | 少把差结果放进长任务 |
| 4 | 再打磨站点细分类与复杂交互 | 锦上添花 |
